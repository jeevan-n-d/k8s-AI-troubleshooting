# Section 4 – Complete Backend Architecture (How Everything Works Internally)

This section explains the **entire backend** — how a request flows through FastAPI, how Kubernetes data is collected, how the AI module is invoked, and how the response is returned to the frontend.

---

## 1. Backend Architecture

Your backend is built using **FastAPI** because it provides:

- High performance
- Automatic API documentation (Swagger)
- Easy JSON handling
- Async support
- Simple routing
- Good Python ecosystem

The backend is the **brain** of the entire application.

---

## 2. Backend Folder Structure

Your backend is organized like this:

```text
backend/
│
├── app/
│
├── ai/
│      reasoner.py
│
├── api/
│      endpoints.py
│
├── core/
│      config.py
│
├── kubernetes/
│      executor.py
│      inspector.py
│      service.py
│
├── models/
│      schemas.py
│
├── services/
│      troubleshooter.py
│
└── main.py
```

Every folder has one responsibility.

---

## 3. app/main.py

This is the application entry point. Think of it as:

```text
Power Button
  ↓
Start FastAPI
  ↓
Load Routes
  ↓
Application Ready
```

When Docker starts:

```bash
uvicorn app.main:app
```

FastAPI starts listening, e.g. on `localhost:8000`. Now the frontend can send requests.

---

## 4. API Layer

The folder `api/` contains `endpoints.py`. This file defines every REST endpoint, for example:

```text
GET  /pods
GET  /nodes
GET  /contexts
GET  /cluster/info
POST /investigate
```

Think of endpoints as **doors**. The user knocks on one door, and the backend executes the required logic.

---

## 5. Request Lifecycle

Suppose the user presses **Investigate**:

```text
Browser
  ↓
POST /investigate
  ↓
FastAPI Router
  ↓
Investigation Function
  ↓
Kubernetes Service
  ↓
AI
  ↓
JSON Response
```

This is the complete lifecycle.

---

## 6. Kubernetes Layer

The folder `kubernetes/` is responsible only for talking to Kubernetes. It should never contain AI logic or frontend logic.

**Responsibilities:**
- Run kubectl
- Parse output
- Return structured data

---

## 7. executor.py

This file is the lowest level. Its only responsibility is to execute kubectl commands.

```python
subprocess.run(...)
```

Think of it as:

```text
Python
  ↓
Command
  ↓
kubectl
  ↓
Output
```

Nothing more.

---

## 8. inspector.py

The executor simply executes commands. The inspector understands Kubernetes.

**Instead of** writing `kubectl get pods` everywhere, the inspector provides:

```python
inspect_pods()
```

Internally:

```text
inspect_pods()
  ↓
executor.run()
  ↓
kubectl get pods
  ↓
Return JSON
```

This keeps the code clean.

---

## 9. service.py

This combines everything. Instead of the frontend calling Pods, Nodes, Deployments, and Services one by one, `service.py` performs:

```text
Collect Everything
```

```text
Pods + Nodes + Deployments + Events + Logs
       ↓
Cluster Snapshot
```

This snapshot becomes the AI input.

---

## 10. AI Folder

```text
ai/
  reasoner.py
```

The reasoner does not know how Kubernetes works — it simply receives data:

```text
Cluster Snapshot
  ↓
Prompt
  ↓
OpenRouter
  ↓
LLM
  ↓
Diagnosis
```

---

## 11. services/

Example: `troubleshooter.py`

Think of this as the **orchestrator**. It coordinates everything:

```text
Collect Cluster
  ↓
Collect Logs
  ↓
Collect Events
  ↓
Build Prompt
  ↓
Call AI
  ↓
Return Report
```

Instead of writing all this inside one endpoint, it's separated into a service. This is much cleaner.

---

## 12. models/

This folder contains `schemas.py` — Pydantic models, for example:

```python
class InvestigationResponse:
```

These define:
- Request format
- Response format
- Validation

**Benefit:** if the frontend sends invalid JSON, FastAPI automatically rejects it.

---

## 13. core/

Example: `config.py`

Contains configuration, such as:
- API Keys
- Model Name
- Environment Variables
- KUBECONFIG Path

Instead of hardcoding values everywhere, everything comes from one location.

---

## 14. Environment Variables

**Instead of:**
```python
API_KEY = "abc123"
```

The backend reads:
```text
OPENROUTER_API_KEY
```

Similarly:
```text
KUBECONFIG_PATH
OPENROUTER_MODEL
PORT
HOST
```

This makes deployment easier.

---

## 15. Docker Container

The backend runs inside Docker:

```text
Python
  ↓
FastAPI
  ↓
kubectl
  ↓
Application
```

Docker ensures the same environment across every computer and every deployment.

---

## 16. Docker Compose

Docker Compose starts Frontend and Backend at once:

```bash
docker compose up
```

creates:
```text
Container 1 — Frontend
Container 2 — Backend
```

The backend also mounts `/root/.kube` to access Kubernetes.

---

## 17. How Frontend Talks to Backend

```text
Browser
  ↓
http://localhost:3000
```

Frontend sends:
```http
POST http://localhost:8000/investigate
```

Backend processes and returns:
```json
{
 "severity": "High"
}
```

Frontend displays:
```text
Severity: High
```

---

## 18. Error Handling

Suppose kubectl fails. Instead of crashing, the backend catches the exception:

```text
kubectl
  ↓
Error
  ↓
Python Exception
  ↓
JSON Error
  ↓
Frontend
```

Example response:

```json
{
 "error": "Unable to connect to cluster"
}
```

This is much better than crashing.

---

## 19. Logging

The backend should log steps such as:

```text
Request Received
  ↓
Running kubectl
  ↓
Pods Collected
  ↓
Prompt Created
  ↓
AI Finished
  ↓
Response Returned
```

This helps debugging. Recall that during your debugging you added `/cluster/debug` and logging — that helped identify that Docker wasn't reading the kubeconfig. Logging is essential.

---

## 20. Swagger

FastAPI automatically generates `/docs` — the Swagger UI.

**Benefits:** you can test `GET /pods`, `GET /nodes`, `POST /investigate` without the frontend. Very useful.

---

## 21. Backend Security

The frontend never gets:
- Kubeconfig
- API Keys
- OpenRouter Key

Everything stays inside the backend. Only the backend talks to Kubernetes and OpenRouter. This is proper architecture.

---

## 22. Why the Backend Is Split into Layers

**Bad Design:**
```text
One File → 2000 Lines → Everything Mixed
```

**Good Design:**
```text
API → Service → Kubernetes → AI → Models → Config
```

Each layer has one responsibility.

## 24. Why This Architecture Is Good

Your backend follows good software engineering principles:

- **Separation of concerns**: API, Kubernetes, AI, configuration, and data models each have a distinct responsibility.
- **Maintainability**: Changes in one layer (e.g., replacing `kubectl` with the Kubernetes Python client) can often be isolated to the Kubernetes layer.
- **Security**: Sensitive credentials remain on the backend.
- **Testability**: Each layer can be tested independently.
- **Extensibility**: New features such as multi-cluster support or persistent investigation history can be added without redesigning the entire application.
