# Section 1 – Complete System Architecture

## 1. What Problem Does This Project Solve?

Imagine a DevOps engineer receives this alert:

> "Application is down."

Normally, the engineer manually runs many commands:

```bash
kubectl get pods -A
kubectl describe pod xyz
kubectl logs xyz
kubectl get events
kubectl get nodes
kubectl describe node
kubectl get deployments
kubectl get svc
```

Then they manually analyze issues such as:

- CrashLoopBackOff
- ImagePullBackOff
- Pending Pods
- Failed Scheduling
- OOMKilled
- Node Not Ready
- Missing Services
- Network Issues

This can easily take **10–30 minutes**.

Your platform automates this entire process. Instead of manually debugging Kubernetes, the engineer clicks **Investigate**, and the platform:

1. Collects cluster information.
2. Collects logs.
3. Collects events.
4. Collects pod status.
5. Sends the information to an AI model.
6. AI explains the issue in plain English.
7. AI suggests the fix.

So the platform acts like an **AI-powered Senior Kubernetes Engineer**.

## 3. Major Components

The project has five major parts.

### Component 1 — Frontend

Built using:
- Next.js
- React
- TypeScript
- Tailwind CSS

Its job is **only UI**. It never talks directly to Kubernetes — instead, it talks only to the backend.

**Responsibilities:**
- Login
- Dashboard
- Resources Explorer
- AI Report
- Cluster Statistics
- Cluster Details
- Loading Screens

---

### Component 2 — Backend

Built using:
- FastAPI
- Python

The backend is the brain.

**Responsibilities:**
- Receives requests
- Executes kubectl
- Reads cluster
- Collects data
- Calls AI
- Returns diagnosis

The frontend never executes Kubernetes commands. Only the backend does.

---

### Component 3 — Kubernetes Cluster

This is the infrastructure being monitored. Examples:

```
Docker Desktop Kubernetes
or
kind
or
minikube
or
k3s
```

Currently, your project supports the local cluster because the backend has access to your local kubeconfig. Remote clusters are discussed in detail in Section 2.

---

### Component 4 — AI

Your AI model receives Kubernetes information. It never directly connects to Kubernetes — instead, it receives already-collected data.

Example:
```
Pods
Deployments
Services
Events
Logs
Node Status
Resource Usage
```

Then AI reasons about them.

---

### Component 5 — OpenRouter

Instead of running an LLM on your computer, the backend sends prompts to OpenRouter. OpenRouter forwards them to the selected model.

```
Backend
  ↓
OpenRouter
  ↓
Llama
  ↓
Response
  ↓
Backend
  ↓
Frontend
```

This means your application doesn't need to host the model itself.

Your UI contains:

**Typical flow:**
```
User
  ↓

  ↓

  ↓
```

In the current project, authentication protects the application interface. It is separate from Kubernetes authentication.

---

## 5. Database

Your current implementation **does not use a traditional database** (like PostgreSQL or MySQL) for cluster data.

Instead:
```
Cluster
  ↓
Collect Data
  ↓
Process
  ↓
AI
  ↓
Return
```

The information is fetched live. Nothing is permanently stored.

This is actually a good design because Kubernetes changes every few seconds — storing cluster state permanently would quickly become outdated.

If you later add a database, it could store things like:
- Investigation history
- User accounts
- Saved AI reports
- Previous incidents
- Audit logs
- Favorite clusters

## 6. InsForge Storage

From earlier discussions, InsForge is used as the **platform layer** around your application rather than as the component that collects Kubernetes data.

Its role is to support your application workflow (e.g., project resources, prompts, or managed assets, depending on configuration), while the actual cluster inspection is still performed by your backend through `kubectl`.

The important separation:
```
InsForge
   │
Stores/supports application assets
   │
   ▼
FastAPI Backend
   │
Runs kubectl
   │
Reads Kubernetes
```

So InsForge does **not** replace Kubernetes access.

## 7. Why Frontend Never Talks to Kubernetes

Imagine if JavaScript in the browser executed:
```bash
kubectl get pods
```

That would be a security disaster — anyone could control your cluster.

Instead:
```
Browser
  ↓
Backend
  ↓
kubectl
```

The backend becomes the security boundary. Only trusted server code can access Kubernetes.

---

---

## 10. Why Use REST APIs?

Frontend and backend are separate applications. They communicate using HTTP.

Example:
```
GET /pods
GET /nodes
GET /namespaces
POST /investigate
```

The backend responds with JSON:

```json
{
  "status": "Healthy",
  "pods": 12,
  "nodes": 3
}
```

The frontend renders this into cards, tables, and reports.

---

## 11. Why This Architecture Is Good

**Advantages:**
- Frontend stays lightweight.
- Backend handles sensitive operations.
- Kubernetes credentials remain on the backend.
- AI can be changed without rewriting the frontend.
- Frontend doesn't need Kubernetes knowledge.
- Supports future multi-cluster expansion.
- Easier to secure and maintain.
