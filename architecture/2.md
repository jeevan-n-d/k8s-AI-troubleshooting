# Section 2 – Kubernetes Integration (The Heart of Your Platform)

This is the most important part of your project because **everything depends on the backend successfully talking to the Kubernetes cluster**.

---

## 1. What Is the Backend Actually Doing?

Many people think the AI talks to Kubernetes. **It does not.**

Instead, your backend acts like a DevOps engineer.

```text
Senior DevOps Engineer
  ↓
Runs kubectl
  ↓
Reads output
  ↓
Analyzes issue
```

Your backend does exactly the same thing:

```text
FastAPI Backend
  ↓
Runs kubectl
  ↓
Collects output
  ↓
Sends output to AI
```

The AI never executes Kubernetes commands.

---

## 2. The Most Important Component

The most important component is **kubectl**.

Without kubectl, your backend knows absolutely nothing about Kubernetes.

```text
Frontend
  ↓
Backend
  ↓
kubectl
  ↓
Kubernetes API Server
  ↓
Cluster
```

kubectl is simply a client — it talks to the Kubernetes API Server.

---

## 3. Where Does kubectl Get Cluster Information?

This is where **kubeconfig** comes in.

Every Kubernetes cluster has credentials, stored inside:

```text
Windows
C:\Users\<username>\.kube\config
```

Inside this file:
- Cluster address
- Authentication
- Certificates
- Current Context
- User credentials

Example structure:

```yaml
clusters:
- cluster:
    server: https://localhost:6443

users:
- name: docker-desktop

contexts:
- context:
    cluster: docker-desktop
    user: docker-desktop

current-context: docker-desktop
```

This file tells kubectl:

> "This is the cluster you should talk to."

---

## 4. Why Your Backend Originally Failed

Recall your earlier debugging.

Your backend was running inside Docker. A Docker container has its own filesystem.

```text
Windows
C:\Users\jeeva\.kube\config
```

```text
Backend container
/root/.kube
```

These are completely different locations.

Initially:

```text
Backend
  ↓
kubectl
  ↓
Looks for kubeconfig
  ↓
Not Found
  ↓
No cluster
```

That's exactly why your backend was returning fallback/static data during debugging.

---

## 5. The Fix

You mounted your kubeconfig into Docker.

**Docker Compose:**

```yaml
volumes:
  - ~/.kube:/root/.kube:ro
```

Meaning:

```text
Windows
C:\Users\jeeva\.kube
  ↓
Mounted
  ↓
Container
/root/.kube
```

Now the backend sees exactly the same kubeconfig as Windows.

---

## 6. Why Read-Only?

Notice `:ro` — meaning **Read Only**.

This is important. Your backend can:
- ✅ Read kubeconfig

But cannot:
- ❌ Modify kubeconfig

This prevents accidental corruption.

---

## 7. KUBECONFIG Environment Variable

You also configured:

```text
KUBECONFIG_PATH=/root/.kube/config
```

So the backend knows exactly where to find the kubeconfig.

```text
Backend
  ↓
Read Environment Variable
  ↓
Locate kubeconfig
  ↓
Run kubectl
```

## 8. How the Backend Gets Real Cluster Information

When the user presses **Investigate**, the backend executes commands, for example:

```bash
kubectl get pods -A -o json
```

Notice `-o json` — this is extremely important.

The backend does **not** read terminal text. Instead, kubectl returns JSON:

```json
{
  "items": [
    {
      "metadata": {},
      "status": {}
    }
  ]
}
```

JSON is much easier for Python to parse.

## 10. Where Are These Commands Executed?

Not inside the browser. Not inside the AI. Inside **Python**.

Simplified code:

```python
result = subprocess.run(
    ["kubectl", "get", "pods", "-A", "-o", "json"],
    capture_output=True,
    text=True
)
```

Python waits, kubectl finishes, and the output becomes `result.stdout`. Then:

```python
json.loads(result.stdout)
```

Now Python has a dictionary → objects → lists → pod information.

---

## 11. How the Backend Converts Kubernetes Output into Python

Suppose kubectl returns:

```json
{
 "items": [
   {
      "metadata": {
         "name": "frontend"
      },
      "status": {
         "phase": "Running"
      }
   }
 ]
}
```

Python converts this to:

```python
pods[0]["metadata"]["name"]
# → frontend
```

```python
pods[0]["status"]["phase"]
# → Running
```

Now the backend can easily analyze it.

## 14. Why the Dashboard Filters System Namespaces

System namespaces include:
```text
kube-system
kube-public
kube-node-lease
default
```

These contain Kubernetes infrastructure. Users usually care about application namespaces. Therefore:

- **Dashboard** → filters system namespaces
- **Resources Explorer** → shows everything

That's exactly the UI behavior you implemented.

## 16. Why the Local Cluster Works

Your kubeconfig contains `docker-desktop` or `kind`. These clusters exist on your computer. The backend container can reach them because:

```text
Backend
  ↓
Docker Network
  ↓
Docker Desktop Kubernetes
  ↓
API Server
```

Everything runs on the same machine.

---

## 17. Why Remote Clusters Don't Automatically Work

Suppose the cluster is on GKE. Your backend needs:
- kubeconfig
- credentials
- network access
- VPN (if private)
- firewall permissions

Without these, kubectl cannot connect:

```text
kubectl → API Server → Connection refused
```
or
```text
Unauthorized
```
or
```text
Certificate error
```

The backend is capable of working with remote clusters, but only after it's given valid credentials and network connectivity.

## 20. Key Takeaways

After Section 2, you should understand these core ideas:

- **`kubectl` is the bridge** between your backend and Kubernetes.
- **`kubeconfig` tells `kubectl` how to authenticate and which cluster to use.**
- Your backend runs `kubectl` commands, collects **live JSON**, and parses it with Python.
- The dashboard and resource explorer display data generated from those live API calls rather than hardcoded values.
- The AI model **does not query Kubernetes directly**. It only analyzes the structured data prepared by the backend.
