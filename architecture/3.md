
**This is NOT how your project works.** Instead, your platform follows a proper AI pipeline.

---

## 2. Why AI Doesn't Connect Directly to Kubernetes

Imagine giving ChatGPT direct cluster access. It could theoretically execute commands like:

```bash
kubectl delete pods --all
```
or
```bash
kubectl scale deployment app --replicas=0
```

That would be extremely dangerous. Instead, your architecture is:

```text
AI
 ↓
Read Only Data
 ↓
Reason
 ↓
Suggest
 ↓
Done
```

The AI never has cluster credentials. It never executes commands. It only analyzes information — much safer.

---

## 3. Step 1 — Collect Kubernetes Information

Before AI starts thinking, the backend collects everything, e.g.:

```bash
kubectl get pods -A -o json
kubectl get nodes -o json
kubectl get deployments -A -o json
kubectl get events -A -o json
kubectl logs failing-pod
```

Now the backend has:
```text
Pods
Nodes
Events
Logs
Services
Deployments
Namespaces
```

---

## 4. Step 2 — Convert Everything into Python Objects

Suppose Kubernetes returns:

```json
{
 "metadata": {
   "name": "frontend"
 },
 "status": {
   "phase": "Running"
 }
}
```

Python converts this into:

```python
pod.name
# → frontend

pod.status
# → Running
```

Now the backend can inspect everything programmatically.

---

## 5. Step 3 — Data Cleaning

Kubernetes JSON is huge — one Pod can contain hundreds of fields. AI doesn't need everything, so the backend extracts only useful information.

**Instead of sending:**
```json
{
  "managedFields": {},
  "resourceVersion": "123",
  "uid": "....",
  ...
}
```

**Backend creates:**
```json
{
 "pod": "frontend",
 "status": "CrashLoopBackOff",
 "restarts": 7
}
```

Much cleaner, much cheaper, much faster.

---

## 6. Step 4 — Merge Cluster Information

The backend creates one investigation object:

```text
Pods + Nodes + Events + Logs + Deployments + Services
       ↓
Investigation Data
```

Instead of dozens of API responses, the AI receives one structured object.

---

## 7. Step 5 — Build the AI Prompt

This is called **Prompt Engineering**.

**Instead of asking:**
```text
Why is my cluster broken?
```

**The backend builds something like:**
```text
You are a Senior Kubernetes DevOps Engineer.

Analyze the following cluster.

Pods:
frontend — CrashLoopBackOff
backend — Running

Node:
Ready

Events:
BackOff restarting container

Logs:
Connection refused — database
```

The AI receives **facts**, not opinions.

---

## 8. Why Prompt Engineering Matters

**A bad prompt:**
```text
Analyze Kubernetes.
```
Produces vague answers.

**A good prompt says:**
```text
Act as a Senior Kubernetes Engineer.

Explain:
1. Root Cause
2. Severity
3. Why it happened
4. Best Fix
5. Preventive Measures
```

This gives consistent results.

---

## 9. Step 6 — Send Prompt to OpenRouter

```text
Backend
  ↓
HTTPS Request
  ↓
OpenRouter
  ↓
Selected Model
```

Example payload:

```json
{
 "model": "meta-llama/llama-3-70b-instruct",
 "messages": [
   {
      "role": "user",
      "content": "..."
   }
 ]
}
```

OpenRouter forwards the request to the selected model.

---

## 10. Why Use OpenRouter?

Instead of integrating separately with every LLM provider:

```text
Backend
  ↓
OpenRouter
  ↓
Llama / Mistral / DeepSeek / Gemma
```

Changing models often only requires changing the configured model name rather than rewriting your application logic.

## 13. How AI Determines Severity

| Status | Severity |
|---|---|
| Running | Healthy |
| Pending | Medium |
| CrashLoopBackOff | High |
| Node Not Ready | Critical |

The backend or the prompt can guide the model to classify issues consistently.

---

## 14. How AI Finds Root Cause

**Example 1:**
- Events: `ImagePullBackOff`
- Logs: `Image not found`
- AI concludes: *Container image cannot be pulled.*

**Example 2:**
- Events: `FailedScheduling`
- Node: `Memory Pressure`
- AI concludes: *Cluster doesn't have enough resources.*

---

## 15. How AI Generates Recommendations

**Problem:** `OOMKilled`
**AI suggests:**
- Increase memory limit
- OR reduce application memory usage

**Problem:** `ImagePullBackOff`
**Recommendation:**
- Verify image name
- Verify registry
- Verify image tag

**Problem:** `CrashLoopBackOff`
**Recommendation:**
- Inspect application logs
- Check dependencies
- Verify configuration

## 21. Why This AI Architecture Is Good

**Advantages:**
- AI cannot accidentally modify the cluster.
- Only relevant data is sent to the model.
- The backend controls what the AI sees.
- The AI focuses on reasoning instead of data collection.
- Different LLMs can be swapped with minimal backend changes.
- Kubernetes access remains isolated to the backend.

## One Important Improvement for the Future

Right now, your AI performs **one-shot analysis**: the backend collects data, sends it to the LLM, and returns the result.

A future enhancement would be an **AI agent** that can decide what to inspect next. For example:

```text
Initial investigation
        │
        ▼
LLM notices CrashLoopBackOff
        │
        ▼
Requests pod logs
        │
        ▼
Backend fetches logs
        │
        ▼
LLM requests pod description
        │
        ▼
Backend fetches describe output
        │
        ▼
LLM produces a more precise diagnosis
```

That kind of iterative reasoning is what many modern AI agents use, and it would be a strong future extension for your platform.
