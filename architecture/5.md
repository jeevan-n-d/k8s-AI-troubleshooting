## 3. Authentication

User enters:
```text
Email
Password
```

Frontend sends:
```http
POST /login
```

Backend verifies the user and returns a **JWT / Session Token**. The frontend stores it, and every future request includes this token.

Authentication protects **your application**, not Kubernetes.

---

## 4. Dashboard Loads

Dashboard requests:
```http
GET /cluster/info
```

Backend executes:
```bash
kubectl get nodes
kubectl get pods
kubectl get deployments
kubectl get namespaces
```

Returns:
```json
{
 "pods": 15,
 "nodes": 3,
 "deployments": 4
}
```

Dashboard updates: **Pods: 15**, **Nodes: 3**, etc.


The frontend does **nothing intelligent** here — it only sends the request.

## 6. Backend Investigation Begins

Backend receives `POST /investigate` and starts orchestrating everything — think of it as the **Investigation Manager**:

```text
Collect → Analyze → Return
```

---

## 7. Kubernetes Collection

Backend starts collecting:

| Command | Returns |
|---|---|
| `kubectl get pods -A -o json` | Pods |
| `kubectl get nodes -o json` | Nodes |
| `kubectl get deployments -A -o json` | Deployments |
| `kubectl get svc -A -o json` | Services |
| `kubectl get events -A -o json` | Events |
| `kubectl logs pod-name` (if needed) | Logs |

Everything is collected.

---

## 8. Real-Time Collection

One important feature: your backend **never reads saved files**. It always executes `kubectl` **now**.

So if a pod crashed 10 seconds ago, the backend immediately sees it. No cache, no database — everything is live.

---

## 9. Why the Dashboard Updates Automatically

```text

  ↓
New output
```

## 10. AI Pipeline Starts

Now the backend has Pods, Nodes, Deployments, Events, Logs, Namespaces, and Services. It combines everything into one investigation object — the **Cluster Snapshot**.

This snapshot becomes the AI input.

## 19. Why Only the Local Cluster Works Right Now

Your backend reads `~/.kube/config`, mounted into the Docker container. That kubeconfig points to your local Docker Desktop Kubernetes cluster.

For a remote cluster (EKS, GKE, AKS, or on-premises), you would need:
- A kubeconfig or credentials for that cluster.
- Network access to its Kubernetes API server.
- Appropriate authentication (certificates, tokens, cloud IAM, etc.).

Once those are configured, the same backend logic can query a remote cluster as well.

## 20. Current Limitations

Your current version performs one investigation at a time. It doesn't:
- Monitor continuously
- Compare yesterday vs. today
- Detect trends
- Remember previous investigations
- Automatically alert users

These are opportunities for future development.

## 21. Future Improvements

### Multi-cluster
Instead of one kubeconfig, support AWS, Azure, GCP, on-prem, kind, minikube.

```text
User selects cluster → Backend switches context → Runs kubectl
```

### Database
Store AI reports, investigation history, users, saved incidents, and audit logs.

### Background Monitoring

```text
Every minute
  ↓
Collect cluster
  ↓
Compare
  ↓
Detect failures
  ↓
Notify user
```

Instead of waiting for someone to click **Investigate**, the platform could proactively detect issues.

### AI Agent

**Current:**
```text
Collect → AI → Answer
```

**Future:**
```text
Collect → AI → Needs logs → Collect logs → Needs describe
→ Collect describe → Needs events → Collect events → Better diagnosis
```

This creates a much more capable troubleshooting assistant.

### Metrics Integration

A future version could include metrics from systems like Prometheus, allowing the AI to reason about:
- CPU usage
- Memory usage
- Network traffic
- Historical trends

This would improve diagnosis quality.

## 24. Interview Explanation (2–3 Minutes)

If an interviewer asks:

> **"Explain your Kubernetes AI Troubleshooting Platform."**

You can answer:

> "I built a full-stack Kubernetes AI Troubleshooting Platform using Next.js for the frontend and FastAPI for the backend. The frontend communicates with the backend through REST APIs. When a user starts an investigation, the backend uses `kubectl` with the configured kubeconfig to collect live Kubernetes data such as pods, nodes, deployments, services, events, and logs. The backend parses this information into structured Python objects, builds a prompt containing the relevant cluster state, and sends it to an LLM through OpenRouter. The model analyzes the cluster state and returns a diagnosis, severity, recommendations, and preventive best practices. The backend returns this structured response as JSON, and the frontend displays it as an AI-generated troubleshooting report. The current implementation targets a local Kubernetes cluster, but the architecture can be extended to support multiple remote clusters by supplying the appropriate kubeconfig and credentials."

## One Final Observation

From everything discussed over the last several conversations, this project demonstrates several practical engineering skills rather than just AI integration:

- Designing a full-stack application with clear separation between frontend, backend, Kubernetes integration, and AI reasoning.
- Working with Kubernetes programmatically through `kubectl` and `kubeconfig`.
- Building REST APIs with FastAPI.
- Integrating external LLM services through OpenRouter.
- Debugging real infrastructure issues (like Docker container access to the local kubeconfig).
- Structuring code into maintainable layers instead of placing all logic in a single file.

Those are the aspects that are likely to stand out most in interviews, especially when you can explain not just **what** the application does, but **why** you designed it this way and how you solved the integration challenges along the way.
